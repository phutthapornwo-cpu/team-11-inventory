# Spec: ฟีเจอร์แจ้งเตือนสต็อกต่ำและรายงานมูลค่าสต็อก

## 1. เป้าหมาย (Goal)

พัฒนาระบบจัดการคลังสินค้า (Inventory Management System) ให้สามารถบันทึกการรับและจ่ายสินค้า พร้อมปรับปรุงจำนวนสต็อกทันที ตรวจสอบและแจ้งเตือนเมื่อสินค้าเหลือน้อยกว่าหรือเท่ากับค่าขั้นต่ำที่กำหนด (Threshold) และสร้างรายงานมูลค่าสต็อกแยกตามหมวดหมู่ เพื่อช่วยให้ผู้จัดการวางแผนการสั่งซื้อและบริหารงบประมาณได้อย่างมีประสิทธิภาพ

ระบบจะใช้การแจ้งเตือนผ่านข้อความใน CLI (จำลองการส่ง Email/SMS) โดยยังไม่ส่งข้อความผ่านบริการภายนอกจริง และจะใช้การจัดเก็บข้อมูลตามรูปแบบที่โปรเจกต์รองรับ

## 2. User Stories

| รหัส | User Story |
|---|---|
| US-01 | As a พนักงานคลังสินค้า, I want บันทึกการรับและจ่ายสินค้าพร้อมอัปเดตสต็อกทันที, so that จำนวนสินค้าในระบบตรงกับการดำเนินงานจริง |
| US-02 | As a ผู้จัดการ, I want รับการแจ้งเตือนเมื่อสต็อกสินค้าต่ำกว่าหรือเท่ากับ Threshold, so that สามารถวางแผนสั่งซื้อก่อนสินค้าไม่เพียงพอ |
| US-03 | As a ผู้จัดการ, I want ดูรายงานมูลค่าสต็อกแยกตามหมวดหมู่, so that สามารถวิเคราะห์มูลค่าสินค้าคงคลังและวางแผนงบประมาณได้ |
| US-04 | As a ผู้จัดการ, I want กำหนด Threshold ให้สินค้าแต่ละรายการได้, so that สามารถกำหนดระดับสต็อกขั้นต่ำให้เหมาะสมกับสินค้าแต่ละชนิด |
| US-05 | As a ผู้ดูแลระบบ, I want เลือกช่องทางการแจ้งเตือนที่ระบบรองรับได้, so that สามารถเพิ่มหรือเปลี่ยนช่องทางการแจ้งเตือนได้โดยไม่ต้องแก้ไข Business Logic ของการจัดการสต็อก |

**ข้อกำหนดเพิ่มเติม**

- US-04: Threshold ต้องเป็นจำนวนที่ไม่ติดลบ และต้องปฏิเสธค่าที่ไม่ถูกต้อง
- US-05: ในขอบเขตปัจจุบัน ระบบรองรับการแจ้งเตือนผ่าน CLI โดยจำลอง Email/SMS การส่งจริงยังไม่อยู่ในขอบเขต
- การเปลี่ยน Threshold ต้องไม่เปลี่ยนจำนวนสต็อกปัจจุบันของสินค้า

## 3. Acceptance Criteria (Given-When-Then)

### 3.1 US-01: การรับและจ่ายสินค้า

**Scenario 1: รับสินค้าเข้าคลังสำเร็จ**

```gherkin
Scenario: รับสินค้าเข้าคลัง
  Given สินค้ามีจำนวนคงเหลือ 10 ชิ้น
  When พนักงานบันทึกรับสินค้าเพิ่ม 5 ชิ้น
  Then จำนวนคงเหลือต้องเป็น 15 ชิ้น
  And ระบบต้องแสดงผลการรับสินค้าสำเร็จ
```

**Scenario 2: จ่ายสินค้าออกจากคลังสำเร็จ**

```gherkin
Scenario: จ่ายสินค้าเมื่อมีสต็อกเพียงพอ
  Given สินค้ามีจำนวนคงเหลือ 20 ชิ้น
  When พนักงานบันทึกจ่ายออก 8 ชิ้น
  Then จำนวนคงเหลือต้องเป็น 12 ชิ้น
  And ระบบต้องแสดงผลการจ่ายสินค้าสำเร็จ
```

**Scenario 3: ปฏิเสธการจ่ายสินค้าเมื่อจำนวนไม่เพียงพอ**

```gherkin
Scenario: จ่ายสินค้าเกินจำนวนคงเหลือ
  Given สินค้ามีจำนวนคงเหลือ 5 ชิ้น
  When พนักงานบันทึกจ่ายออก 8 ชิ้น
  Then ระบบต้องปฏิเสธรายการจ่ายสินค้า
  And จำนวนคงเหลือต้องยังเป็น 5 ชิ้น
  And ระบบต้องแจ้งเหตุผลว่าจำนวนสินค้าไม่เพียงพอ
```

**Scenario 4: ปฏิเสธจำนวนรับหรือจ่ายที่ไม่ถูกต้อง**

```gherkin
Scenario: ระบุจำนวนสินค้าที่ไม่ถูกต้อง
  Given สินค้ามีจำนวนคงเหลือ 10 ชิ้น
  When พนักงานระบุจำนวนรับหรือจ่ายเป็น 0 หรือติดลบ
  Then ระบบต้องปฏิเสธรายการ
  And จำนวนคงเหลือต้องยังเป็น 10 ชิ้น
```

### 3.2 US-02: การแจ้งเตือนสต็อกต่ำ

**Scenario 1: จ่ายสินค้าแล้วสต็อกต่ำกว่า Threshold**

```gherkin
Scenario: จ่ายสินค้าจนสต็อกต่ำกว่า Threshold
  Given สินค้า "สายไฟ 2.5 sq.mm" มีสต็อก 20 เมตร
  And Threshold เท่ากับ 15 เมตร
  When พนักงานบันทึกจ่ายออก 8 เมตร
  Then สต็อกคงเหลือต้องเป็น 12 เมตร
  And ระบบต้องแจ้งเตือนผู้จัดการว่าสต็อกต่ำ
```

**Scenario 2: สต็อกคงเหลือเท่ากับ Threshold**

```gherkin
Scenario: สต็อกคงเหลือเท่ากับ Threshold
  Given สินค้ามีสต็อก 20 ชิ้น
  And Threshold เท่ากับ 15 ชิ้น
  When พนักงานบันทึกจ่ายออก 5 ชิ้น
  Then สต็อกคงเหลือต้องเป็น 15 ชิ้น
  And ระบบต้องแจ้งเตือนผู้จัดการ
```

**Scenario 3: สต็อกยังสูงกว่า Threshold**

```gherkin
Scenario: สต็อกคงเหลือสูงกว่า Threshold
  Given สินค้ามีสต็อก 50 ชิ้น
  And Threshold เท่ากับ 15 ชิ้น
  When พนักงานบันทึกจ่ายออก 10 ชิ้น
  Then สต็อกคงเหลือต้องเป็น 40 ชิ้น
  And ระบบต้องไม่ส่งการแจ้งเตือนสต็อกต่ำ
```

**Scenario 4: ปฏิเสธรายการจ่ายสินค้า**

```gherkin
Scenario: จ่ายสินค้าไม่สำเร็จ
  Given สินค้ามีสต็อก 5 ชิ้น
  And Threshold เท่ากับ 3 ชิ้น
  When พนักงานพยายามจ่ายออก 8 ชิ้น
  Then ระบบต้องปฏิเสธรายการจ่าย
  And สต็อกต้องยังเป็น 5 ชิ้น
  And ระบบต้องไม่ส่งการแจ้งเตือนจากรายการจ่ายที่ถูกปฏิเสธ
```

**กติกาการแจ้งเตือน**

- ตรวจสอบจำนวนสต็อกหลังจากรายการรับหรือจ่ายที่สำเร็จ
- แจ้งเตือนเมื่อ `quantity <= threshold`
- ไม่แจ้งเตือนจากรายการที่ไม่สำเร็จ
- ในเวอร์ชันนี้แจ้งเตือนผ่าน CLI โดยจำลองการส่ง Email/SMS
- หากมีการแจ้งเตือนซ้ำจากการทำรายการหลายครั้ง ให้ถือเป็นการแจ้งเตือนตามเหตุการณ์ที่เกิดขึ้น โดยยังไม่กำหนดระบบป้องกันการแจ้งเตือนซ้ำ

### 3.3 US-03: รายงานมูลค่าสต็อกแยกตามหมวดหมู่

**Scenario 1: คำนวณมูลค่าสต็อกแยกตามหมวดหมู่**

```gherkin
Scenario: สร้างรายงานมูลค่าสต็อก
  Given มีสินค้าในหมวดหมู่ Electrical จำนวน 2 รายการ
  And สินค้า A มีจำนวน 10 ชิ้น ราคาต่อหน่วย 100 บาท
  And สินค้า B มีจำนวน 5 ชิ้น ราคาต่อหน่วย 200 บาท
  When ผู้จัดการเรียกดูรายงานมูลค่าสต็อก
  Then มูลค่าหมวด Electrical ต้องเป็น 2000 บาท
  And ระบบต้องแสดงจำนวนรายการและมูลค่ารวมของหมวดหมู่
```

**Scenario 2: สินค้าคงเหลือเป็นศูนย์**

```gherkin
Scenario: รายงานสินค้าที่ไม่มีสต็อก
  Given สินค้าในหมวดหมู่ Plumbing มีจำนวนคงเหลือ 0 ชิ้น
  And ราคาต่อหน่วยเท่ากับ 150 บาท
  When ผู้จัดการเรียกดูรายงานมูลค่าสต็อก
  Then มูลค่าของสินค้ารายการนี้ต้องเป็น 0 บาท
  And ระบบต้องไม่คำนวณมูลค่าติดลบ
```

**Scenario 3: คำนวณมูลค่ารวมทุกหมวดหมู่**

```gherkin
Scenario: คำนวณมูลค่าสต็อกรวม
  Given มีสินค้าอยู่ในหลายหมวดหมู่
  When ผู้จัดการเรียกดูรายงานมูลค่าสต็อก
  Then ระบบต้องแสดงมูลค่ารวมของแต่ละหมวดหมู่
  And มูลค่ารวมทุกหมวดหมู่ต้องเท่ากับผลรวมของมูลค่าสินค้าทั้งหมด
```

### 3.4 US-04: กำหนด Threshold รายสินค้า

**Scenario 1: ตั้งค่า Threshold สำเร็จ**

```gherkin
Scenario: เปลี่ยน Threshold ของสินค้า
  Given สินค้ามี Threshold เท่ากับ 10 ชิ้น
  When ผู้จัดการกำหนด Threshold ใหม่เป็น 20 ชิ้น
  Then ระบบต้องบันทึก Threshold เป็น 20 ชิ้น
  And จำนวนสต็อกปัจจุบันต้องไม่เปลี่ยนแปลง
```

**Scenario 2: ปฏิเสธ Threshold ที่ไม่ถูกต้อง**

```gherkin
Scenario: กำหนด Threshold ติดลบ
  Given สินค้ามี Threshold เท่ากับ 10 ชิ้น
  When ผู้จัดการกำหนด Threshold ใหม่เป็น -1
  Then ระบบต้องปฏิเสธค่าใหม่
  And Threshold เดิมต้องไม่เปลี่ยนแปลง
```

### 3.5 US-05: การเลือกช่องทางแจ้งเตือน

**Scenario 1: ใช้ช่องทาง CLI ที่รองรับ**

```gherkin
Scenario: แจ้งเตือนผ่าน CLI
  Given ระบบตั้งค่าให้ใช้ช่องทาง CLI
  And สินค้ามีจำนวนคงเหลือน้อยกว่าหรือเท่ากับ Threshold
  When ระบบตรวจพบสต็อกต่ำหลังรายการสำเร็จ
  Then ระบบต้องแสดงข้อความแจ้งเตือนผ่าน CLI
```

**Scenario 2: ช่องทางแจ้งเตือนไม่รองรับ**

```gherkin
Scenario: เลือกช่องทางที่ไม่มีการติดตั้ง
  Given ระบบยังไม่รองรับช่องทางแจ้งเตือนที่เลือก
  When ระบบพยายามใช้ช่องทางดังกล่าว
  Then ระบบต้องแจ้งข้อผิดพลาดอย่างชัดเจน
  And ระบบต้องไม่ทำให้การอัปเดตสต็อกที่สำเร็จแล้วถูกย้อนกลับ
```

## 4. In Scope / Out of Scope

### In Scope

1. เพิ่มสินค้าและตรวจสอบข้อมูลสินค้าตามความสามารถเดิมของระบบ
2. บันทึกการรับและจ่ายสินค้า พร้อมอัปเดตจำนวนคงเหลือในหน่วยความจำทันที
3. ปฏิเสธรายการจ่ายที่มีจำนวนมากกว่าสต็อกคงเหลือ
4. ตรวจสอบ Threshold หลังรายการรับหรือจ่ายที่สำเร็จ
5. แจ้งเตือนผ่าน CLI โดยจำลองช่องทาง Email/SMS
6. กำหนด Threshold ให้สินค้าแต่ละรายการ
7. สร้างรายงานมูลค่าสต็อกแยกตามหมวดหมู่และมูลค่ารวมทั้งหมด
8. ทดสอบฟังก์ชันด้วย Automated Tests

### Out of Scope

1. การส่ง Email/SMS จริงผ่านผู้ให้บริการภายนอก
2. ระบบ Login, Authentication และการกำหนดสิทธิ์ผู้ใช้
3. การเชื่อมต่อฐานข้อมูลถาวร เช่น MySQL หรือ PostgreSQL
4. ระบบแจ้งเตือนผ่าน Push Notification
5. ระบบจัดซื้อสินค้าอัตโนมัติ
6. ระบบป้องกันการแจ้งเตือนซ้ำและการจัดการประวัติการแจ้งเตือนแบบถาวร

**การจัดเก็บข้อมูล:** ข้อมูลในขอบเขตของฟีเจอร์นี้เก็บในหน่วยความจำระหว่างที่โปรแกรมทำงาน หากโปรเจกต์ยังใช้ JSON Persistence สำหรับข้อมูลเดิม ให้คงพฤติกรรมเดิมนั้นไว้ โดยไม่ถือว่าเป็นฐานข้อมูลถาวร

## 5. Functional Requirements (FR)

| รหัส | ความต้องการ | จาก Story |
|---|---|---|
| FR-01 | ระบบต้องอัปเดตสต็อกทันทีหลังบันทึกรับหรือจ่ายสินค้าสำเร็จ | US-01 |
| FR-02 | ระบบต้องตรวจสอบสต็อกก่อนจ่าย และปฏิเสธรายการเมื่อจำนวนไม่เพียงพอ | US-01 |
| FR-03 | ระบบต้องตรวจสอบสต็อกหลังรายการรับหรือจ่ายที่สำเร็จ และแจ้งเตือนเมื่อจำนวนคงเหลือน้อยกว่าหรือเท่ากับ Threshold | US-02 |
| FR-04 | ระบบต้องคำนวณมูลค่าสินค้าโดยใช้จำนวนคงเหลือคูณราคาต่อหน่วย และรวมมูลค่าแยกตามหมวดหมู่ | US-03 |
| FR-05 | ระบบต้องให้ผู้จัดการกำหนด Threshold รายสินค้าได้ โดยค่าต้องเป็นตัวเลขที่ไม่ติดลบ | US-04 |
| FR-06 | ระบบต้องแยกส่วนการแจ้งเตือนออกจาก Business Logic ของการจัดการสต็อก และรองรับการเพิ่มช่องทางแจ้งเตือนผ่าน Interface หรือโครงสร้างที่เหมาะสม | US-05 |
| FR-07 | ระบบต้องปฏิเสธจำนวนรับหรือจ่ายที่เป็นศูนย์หรือติดลบ | US-01 |
| FR-08 | ระบบต้องแสดงผลรายงานมูลค่าสต็อกของแต่ละหมวดหมู่และมูลค่ารวมทั้งหมด | US-03 |
| FR-09 | ระบบต้องไม่เปลี่ยนแปลงสต็อกหรือ Threshold เมื่อรายการถูกปฏิเสธ | US-01, US-04 |
| FR-10 | ระบบต้องแสดงข้อความผิดพลาดที่เข้าใจได้เมื่อข้อมูลไม่ถูกต้องหรือช่องทางแจ้งเตือนไม่รองรับ | US-01, US-04, US-05 |

## 6. Non-Functional Requirements (NFR)

| รหัส | มิติ | ความต้องการที่วัดผลได้ |
|---|---|---|
| NFR-01 | Performance | การสร้างรายงานมูลค่าสต็อกสำหรับสินค้า 1,000 รายการต้องเสร็จภายใน 1 วินาที ภายใต้สภาพแวดล้อมทดสอบที่กำหนด |
| NFR-02 | Maintainability | การเพิ่มช่องทางแจ้งเตือนใหม่ต้องทำได้โดยไม่แก้ไข Business Logic หลักของการรับและจ่ายสินค้า และต้องมี Automated Test สำหรับช่องทางใหม่ |
| NFR-03 | Reliability | เมื่อรายการรับหรือจ่ายไม่ผ่านการตรวจสอบ จำนวนสต็อกต้องไม่เปลี่ยนแปลงในทุกกรณีที่ทดสอบ |
| NFR-04 | Testability | Automated Tests ต้องตรวจสอบเงื่อนไขหลักของ FR ได้ และ Code Coverage ต้องไม่น้อยกว่า 85% ตามเกณฑ์ CI ของโปรเจกต์ |
| NFR-05 | Data Integrity | สต็อกคงเหลือต้องไม่ติดลบ และมูลค่าสินค้าต้องไม่ติดลบเมื่อข้อมูลจำนวนและราคาถูกต้อง |
| NFR-06 | Usability | ข้อความแจ้งเตือนและข้อผิดพลาดผ่าน CLI ต้องระบุผลการทำงานและสาเหตุที่สำคัญให้ผู้ใช้เข้าใจได้ |

## 7. Design Notes

1. แยก Business Logic ของ Inventory ออกจากระบบแจ้งเตือน เพื่อให้ทดสอบและเปลี่ยนช่องทางแจ้งเตือนได้ง่าย
2. ออกแบบระบบแจ้งเตือนให้มี Interface หรือ Abstraction ที่เหมาะสม เช่น `Notifier` และ Implementation สำหรับ CLI
3. ให้ Inventory Service เรียก Notifier หลังอัปเดตสต็อกสำเร็จ และหลังตรวจสอบ Threshold แล้ว
4. หากช่องทางแจ้งเตือนผิดพลาด ต้องไม่ทำให้ข้อมูลสต็อกที่อัปเดตสำเร็จแล้วเสียหาย
5. คำนวณมูลค่าสินค้าจาก `quantity × unit_price` และจัดกลุ่มตาม Category
6. กำหนดให้ Threshold เป็นค่าที่ไม่ติดลบ และจำนวนรับ/จ่ายต้องมากกว่าศูนย์
7. ใช้กติกา `quantity <= threshold` อย่างสม่ำเสมอทั้งในโค้ด Spec และ Automated Tests
8. การทดสอบประสิทธิภาพต้องระบุสภาพแวดล้อม จำนวนรายการ และวิธีวัดเวลาให้สามารถทำซ้ำได้

## 8. Definition of Done

- [ ] การรับและจ่ายสินค้าปรับปรุงจำนวนคงเหลือได้ถูกต้อง
- [ ] ระบบปฏิเสธการจ่ายเกินจำนวนคงเหลือและจำนวนรับ/จ่ายที่ไม่ถูกต้อง
- [ ] ระบบแจ้งเตือนเมื่อ `quantity <= threshold`
- [ ] ระบบไม่แจ้งเตือนจากรายการที่ถูกปฏิเสธ
- [ ] ผู้จัดการสามารถกำหนด Threshold รายสินค้าได้
- [ ] รายงานแสดงมูลค่าแยกตามหมวดหมู่และมูลค่ารวมถูกต้อง
- [ ] มี Automated Tests ครอบคลุมกรณีสำเร็จ กรณีผิดพลาด และขอบเขต Threshold
- [ ] Tests ผ่าน และ Code Coverage ไม่น้อยกว่า 85%
- [ ] Ruff ผ่านตามกฎของโปรเจกต์
- [ ] GitHub Actions ผ่านทุกขั้นตอนที่กำหนด
- [ ] เอกสาร Spec และ Diagram สอดคล้องกับโค้ดที่พัฒนาจริง
